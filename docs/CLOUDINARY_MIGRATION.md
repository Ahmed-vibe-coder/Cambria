# Cloudinary Storage Migration & Security Architecture Report

## 1. Executive Summary & Architectural Shift

### The Underlying Issue
On modern serverless deployment platforms such as Vercel, the application runtime filesystem (`/var/task`) is strictly **read-only** and ephemeral. Any attempt by serverless Route Handlers or Server Actions to write files locally (e.g. `fs.mkdirSync('data/documents')` or `fs.writeFileSync('public/uploads/templates')`) crashes at runtime with `EROFS` or `ENOENT`. Furthermore, even if temporary files were placed in `/tmp`, they do not persist across serverless container cold starts or regional replicas.

### The Solution: Cloudinary Media Storage
Cloudinary has been integrated as the primary, persistent cloud asset storage layer for all **unstructured runtime media**:
1. **Template Studio Background Assets**: User/admin uploaded background artwork for certificates and student ID cards.
2. **Rendered Document Artifacts**: In-memory vector PDF diplomas and high-resolution PNG document thumbnails generated by headless Chromium.

### What Cloudinary Does NOT Do (Critical Boundary)
**Cloudinary is not a database.** It exclusively handles static media blobs. Structured entity records (students, programs, credentials, audit logs, staff users, trusted MFA devices) continue to reside in PostgreSQL.

## 3. Environment Variables & Security Isolation Discipline

### Server-Only Configuration
To avoid exposing sensitive API secrets to browsers, Cloudinary variables are strictly server-side and **never prefixed with `NEXT_PUBLIC_`**:

```env
# Server-Side Only — Strictly isolated from client-side bundles
CLOUDINARY_CLOUD_NAME=kwe1gmrq
CLOUDINARY_API_KEY=677939994143521
CLOUDINARY_API_SECRET=NFF8T6jmZgmelp-NbmN4OEVIn4c
```

### Clean Architecture & Client Isolation
- The browser and client-side components **never** import Cloudinary SDKs or make direct calls to Cloudinary APIs.
- Background image uploads are routed through the administrative `/api/templates/upload` Route Handler which requires an active session and verified MFA.
- Credential document downloads are routed through `/api/documents/[token]/[docType]`, ensuring total access control.

## 4. Security Gating & Revocation Invariant

A central institutional integrity rule governs document access:
> **A credential that is revoked or suspended must NEVER be downloadable or accessible by any user, anywhere.**

### How the Gated Architecture Enforces This Rule:
1. **Never Expose Direct CDN URLs to End Users**:
   Public verification pages, student portals, and email links **never** render raw Cloudinary URLs. All links point to the gated proxy endpoint:
   ```
   /api/documents/[token]/[docType] (e.g. /api/documents/tok_v8K.../certificate)
   /api/documents/[token]/[docType]?thumb=true
   ```
2. **Real-Time Database Status Verification on Every Single Request**:
   When a request arrives at `/api/documents/[token]/[docType]`:
   - It performs an uncached, real-time database query for the credential record.
   - If `status === 'revoked'`:
     - Responds immediately with **`HTTP 403 Forbidden`**.
     - Returns header `X-Credential-Status: revoked`.
     - Returns JSON explaining the revocation reason and timestamp.
     - Never touches Cloudinary or streams any binary data.
   - If `status === 'suspended'`:
     - Responds immediately with **`HTTP 403 Forbidden`**.
     - Returns header `X-Credential-Status: suspended`.
     - Returns JSON explaining the suspension reason.
     - Never touches Cloudinary or streams any binary data.
   - If `status === 'active'`:
     - Securely fetches the asset buffer from Cloudinary server-side.
     - Streams binary PDF (`application/pdf`) or PNG (`image/png`) directly to the client with `Cache-Control: private, no-cache, no-store, must-revalidate`.

## 5. Template Studio Security Controls

Administrative template uploads to Cloudinary enforce four layers of defense:
1. **Session & MFA Gate**: Checks both `cambria_staff_session` and `cambria_staff_mfa_verified` cookies. Unauthenticated or unverified requests receive `401 Unauthorized`.
2. **File Size Enforcement**: Payloads larger than 5MB (`MAX_FILE_SIZE_BYTES = 5 * 1024 * 1024`) are rejected immediately with `400 Bad Request`.
3. **Magic Byte Inspection**: The server reads the first bytes of the binary buffer to verify authentic image headers:
   - PNG: `89 50 4E 47`
   - JPEG: `FF D8 FF`
   - WebP: `52 49 46 46 ... 57 45 42 50`
   Any spoofed payload (e.g. an `.exe`, `.sh`, or `.html` renamed to `.png`) is rejected with `400 Bad Request`.
4. **Non-Guessable Asset Identifiers**: File names are sanitized and assigned cryptographic UUIDs (`template_bg_${Date.now()}_${UUID}`) to prevent path traversal or asset overwrites.

## 7. The Plain Truth on Database Persistence

> **STATUS NOTE**:
> Cloudinary solves file and media storage permanently.
> However, **database persistence on the live Vercel deployment remains an open, separate issue**:
> - Locally, the application uses `@electric-sql/pglite` on disk (`data/postgres`), which cannot run in Vercel serverless containers.
> - On Vercel, Supabase hosted PostgreSQL is connected via public anon key, but queries that insert/update records trigger Supabase RLS error `42501` because `SUPABASE_SERVICE_ROLE_KEY` has not been added to Vercel Project Environment Variables. As a result, database modifications on Vercel fall back to ephemeral container memory.
> - **Adding Cloudinary does not resolve the database RLS issue, and structured records still require the hosted Supabase service role key to be configured in Vercel.**
